# 引擎升级与版本兼容清单（2026-11-13 立）

> 一句话：DSH 引擎在本机是**整目录外部依赖**（不入库，`12-源码照搬/.gitignore:30`），升级不是热更新，是**停机替换**。
> 本文回答三件事：现在有没有新版、换代会变什么、换完怎么验；最后一节是「更新通知」的落点。
> 检查命令：`node 12-源码照搬\工具\引擎更新检查.mjs`（只读，不下载不替换）。

## 一、当前基线（2026-11-13 实测）

| 项 | 值 | 证据 |
|---|---|---|
| 本地引擎 | `0.2.1-rc.3` | `12-源码照搬/引擎/package.json:4` |
| 上游 latest | `0.2.2-rc.1` | npm registry `dist-tags`（本次实测） |
| 上游 next / alpha | `0.2.2-rc.2` / `0.2.2-alpha.3` | 同上 |

**结论：有新版本，且本机 Node 满足新要求**（但换机器/换终端要先看这一条，见 §三.1）。

## 二、换代实测：什么会变、什么不会变

对比方法：从 npm 拉 `0.2.2-rc.1` 的 cli / web-app / workspace / session / storage / client-ui-workspace 六个包，与本机 `0.2.1-rc.3` 逐项 diff。

### 不会变（现契约可继续用）

| 契约 | 实测 |
|---|---|
| CLI 布局与 bin | 两版都是 `lib/bin.js`，`bin.dsh` 字段一致（打包版布局没回退成 `apps/cli/lib/bin.js`） |
| `dsh web` 子命令 | 保留；`--no-open` / `--port` 参数仍在 `bin.js` 的 help 示例里 |
| `bin.js` 差异 | 仅 6 行（版本号与包名引用），无命令解析改动 |
| token 行格式 | 仍是 `dsh web: http://127.0.0.1:<port>/?token=<token>`（`web-app/lib/index.js:162`）⇒ `建会话.mjs` / `main.js` 的正则不用改 |
| RPC 名 | `session/create`、`session/rename`、`session/prompt`、`session/cancel`、`workspace/create`、`workspace/archiveSession`、`workspace/unarchiveSession` 全在（`client-ui-workspace/lib/client.js:2191 / 2524 / 4174`） |
| workspace 服务方法 | `archiveSession` / `unarchiveSession` / `pinSession` 方法集合无增删（新旧差集为空） |
| 设置页 id | `ui-settings-general` 仍在（`web-app/cordis.patch.yml:305`），我们的 `welcomeNoticeVersion` 覆盖继续有效 |

### 会变（必须适配）

| 变化 | 影响 |
|---|---|
| **Node 门槛 `>=24.9.0`** | 0.2.1 没声明，所以 22 也能跑；0.2.2 起 Node 22 直接起不来。本机 24.22.2 满足 |
| 依赖 +4 个包、无移除 | 新增 `dsh-official-bundles` / `dsh-experimental-liveshare` / `dsh-personalized-recommendations` / `dsh-experimental-forge-bundle`；插件名继续存在 |
| `@deepseek-ai/cordis` `~4.0.5` → `~4.1.0` | 插件运行时升一个次版本，**私有插件（`dsh-token-guard`）必须复验** |
| `web-app` 自带 `cordis.patch.yml` 整份替换（约 22 KB） | 默认插件树按 id / insert 组织，我们的覆盖项是否命中要用 `--dump-config` 验收，不能靠"看起来没报错" |
| `profiles/web/node_modules` 随整目录替换消失 | 私有插件落位（junction）必须重跑 `环境适配.mjs --apply`，否则 `ERR_MODULE_NOT_FOUND` |

## 三、适配清单（按层，逐条有判据）

| # | 层 | 要做什么 | 判据 / 命令 | 不做的后果 |
|---|---|---|---|---|
| 1 | 运行时 | Node ≥ 24.9，且**工作台的 PATH 里先命中的那个 node** 也要 ≥24.9 | `& (机器配置.json 里的 nodeExe) -v` | 引擎直接退出（code 1），启动页停住 |
| 2 | 目录布局 | 两套布局都认：打包版 `引擎/lib/bin.js`、源码版 `引擎/apps/cli/lib/bin.js` | `node 外壳\scripts\自检.mjs`（`ENGINE_BINS` 三态） | 误报「缺引擎」，自检恒红一项 |
| 3 | 启动路径 | `main.js` 的 `CLI_BUILT` 只硬编码了源码版路径 ⇒ 打包版下「内置入口」永不命中，每次走 pnpm 兜底 | `server.log` 里 `engine ready in … via pnpm 脚本` | 不是故障，但每次启动多约 10 秒（实测 11.1s） |
| 4 | 配置层 | patch 只按**顶层 id** 匹配；preset group 内的 id 匹配不到，引擎只打 warning 不报错 | `node 引擎\lib\bin.js web --dump-config 2>&1`，数 `patch: entry "…" not found` 必须为 0 | 配置静默失效（以为开了其实没开） |
| 5 | 私有插件 | `插件\<目录>` → `profiles\web\node_modules\<包名>`（junction） | `node 外壳\scripts\环境适配.mjs --apply`，再看 `自检.mjs` 的「私有插件落位」 | 插件 `did not activate` / 起不来 |
| 6 | bundle 可解析 | `profiles/web/package.json` 的 `bundles` 必须能在 profile 或引擎的 `node_modules` 找到 | `环境适配.mjs` 的「bundle 可解析」项 | 引擎起不来（比插件静默失效更早暴露） |
| 7 | 数据层 | 会话 / 凭据 / 技能 / 场景记忆全在 `引擎数据\.dsh`，升级**只换 `引擎/`** | 升级前后会话条数与 `sessions.mjs --check` 命中数一致 | 丢会话（代价最高，且不可再生） |
| 8 | 机器配置 | `机器配置.json` 的 `engineVersion` 会与新引擎 drift | `环境适配.mjs --apply` 对齐 | 版本显示旧值，排查时误导 |
| 9 | 界面版本契约 | `renderers.js` 的 `ADAPTED_ENGINE` 写死 `0.2.1-rc.3`；引擎一变就顶栏变琥珀色 + 提示「跑 `engine-after.mjs` 核对」 | 升级后顶栏是否变琥珀；`grep ADAPTED_ENGINE` | 提示指到一个**不存在的脚本**（见 §五.5） |
| 10 | 端口 | 升级必须停机，`DSH_PORT` 还被占着就换不了目录 | `引擎更新检查.mjs` 的「DSH 端口」行 | 文件锁导致替换失败 |
| 11 | 回退 | 升级前留一份完整 `引擎\` 副本；`引擎数据\.dsh` 另存一份 | 见 §四 第 2 步 | 升坏只能重装，且没有可比对的旧版本 |

## 四、升级 SOP（停机约 10 分钟）

```powershell

node 12-源码照搬\工具\引擎更新检查.mjs          # 有新版本时退出码 1

# 1. 备份（改名前先确认工作台已退出）
Rename-Item -LiteralPath "12-源码照搬\引擎" -NewName "引擎.bak-20261113"
#   会话/凭据另存到工作台外（只复制，不移动）
Robocopy "12-源码照搬\引擎数据\.dsh" "<工作台外的临时目录>\dsh-home-备份" /E

# 2. 换：把新版本整目录放到 12-源码照搬\引擎（内部仍是 lib/ + package.json + node_modules）

# 3. 落位与对齐（幂等，可重复跑）
node 12-源码照搬\外壳\scripts\环境适配.mjs --apply

# 4. 验收四关（缺一关都不算过）
node 12-源码照搬\外壳\scripts\自检.mjs
node 12-源码照搬\引擎\lib\bin.js web --dump-config 2>&1 | Select-String 'not found'   # 应为 0 行
node 12-源码照搬\外壳\scripts\sessions.mjs --check
node 12-源码照搬\外壳\scripts\建会话.mjs --title "升级冒烟" --dry                     # 再看真建 + 归档

# 5. 回退（验收不过时）
#    停工作台 → 删 引擎\ → 引擎.bak-20261113 改回 引擎\ → 环境适配.mjs --apply
```

**RPC 全链路冒烟**（第 4 关的重点，别只看到"引擎起来了"）：真建一条会话 → 改名 → 投一条 prompt（`mode: queue`）→ cancel → `workspace/archiveSession`。这五步覆盖了工作台对引擎的全部写操作，任何一步 HTTP 非 200 都说明契约漂移。

## 五、升级前建议先补的 5 个缺口（都是实测出来的）

| # | 缺口 | 证据 | 影响 |
|---|---|---|---|
| 1 | `工具\引擎快照.mjs` **不存在**，但 `main.js:425` / `main.js:490` 引用它做「正常点快照」与「连续两次启动失败自动回退」 | `Get-ChildItem 工具\` 无此文件；`main.js` 只在 `fs.existsSync` 为真时才跑 | 回退能力实际是空的，日志里连"跳过"都不明显 |

第 3 条的正确写法（`--dump-config` 验证过语义：顶层 patch 匹配不到 group 内条目，必须 `insert`）：

```yaml

      name: "@deepseek-ai/dsh-tool-ask-user"
    - id: tool-present
      name: "@deepseek-ai/dsh-tool-present"
    - id: tool-schedule
      name: "@deepseek-ai/dsh-tool-schedule"
```

⚠️ 改完必须跑 `--dump-config`：`not found` 归零，且 `tool-*` 出现在顶层（缩进 2 空格），才算真挂上。

## 六、「实时更新」能做到什么、做不到什么

| 想做的事 | 能不能 | 说明 |
|---|---|---|
| 实时知道有没有新版 | ✅ | `引擎更新检查.mjs` 查 npm `dist-tags`；npm 官方连不上时自动回落 `registry.npmmirror.com` |
| 后台自动把新版本换上 | ❌ | 整目录替换 + `node_modules` 在 Windows 下被运行中的引擎占用（文件锁），必须停机；且换完必须人工过验收四关 |
| 半自动：检查 → 提示 → 你点一下升 | ✅ | 见 §七 |

结论：**"实时"只做在"发现"这一侧，升级动作保持人工触发**。这不是偷懒——自动替换会在"引擎起不来"时把工作台连数据一起留在半坏状态。

## 七、更新通知：三种落点（选一个或组合）

| 方案 | 改哪里 | 成本 | 断网表现 |
|---|---|---|---|
| A. 顶栏「环境适配」折叠项加一行「引擎更新」 | `main.js`（新 IPC 读状态文件）+ `renderer/topbar-status.js` | M 级（改壳） | 显示"上次检查时间"，不假报已最新 |
| B. 启动时检查一次，有新版弹顶栏 toast | `main.js` 启动链路 | M 级（改启动链路） | 启动会多一次网络请求；建议只读状态文件 |
| C. 定时任务每天跑 `--notify` 写状态文件 | 只加定时任务，不改壳 | L 级（零侵入） | 任务失败不影响工作台 |

**已经有的一处（不改壳也能看见）**：`外壳\scripts\自检.mjs` 新增了「引擎更新」项，跑自检就会打出一行「⚠ 有新版本 0.2.2-rc.1」。适合"我不常开顶栏，跑自检时看"。

## 十、自动更新功能设计（2026-11-13）

> 用户明确：要的不是"版本通知"，是完整功能——**推送（自动下载/替换）+ 回退 + 按钮 + 界面**。
> §六 说过"能实时发现、不能实时换上"，本节的落地方式就是：把"换上"做成一次带停机、带备份、带验收、带自动回退的动作。

### 10.1 可行性已实测（不是推断）

| 事项 | 实测结果 | 结论 |
| --- | --- | --- |
| 完整依赖树能否装出来 | 在 `%TEMP%\dsh-stage-0221` 用 `pnpm 12.18.0` + `registry.npmmirror.com` 装 0.2.2-rc.1：620 包、34358 文件、**526 MB** | 能装，与现网 508 MB 同量级 |
| 第一次装为什么失败 | `ERR_PNPM_IGNORED_BUILDS`：`@deepseek-ai/dsh-subprocess-local` / `@google/genai` / `esbuild` / `koffi` / `node-pty` / `protobufjs` 六个包的后安装脚本被拦 | **必须在 staging 的 `pnpm-workspace.yaml` 里把 `allowBuilds` 六个键显式写成 `true`**，否则自动化必挂 |
| 写死 `allowBuilds: true` 后 | 六个包装完（node-pty 复制了 conpty.dll / OpenConsole.exe，koffi cnoke 预编译完成），`Done in 2.7s`（包体已缓存） | 二次以后极快；首次约 3–6 分钟取决于网络 |
| 装出来的引擎能跑吗 | `node lib\bin.js -V` → `0.2.2-rc.1`；`node lib\bin.js web --dump-config` → 正常输出插件树，exit 0 | **可以在替换前自证，不必先上线再发现坏的** |

| D 盘 staging 建软链失败 | `Failed to create symlink ... os error 2`（pnpm 默认 isolated 布局要给 `.pnpm` 建 symlink，普通权限在 D 盘建不了） | staging 的 `pnpm-workspace.yaml` 写 `nodeLinker: hoisted`（平铺、不建链，与 `profiles/web` 现有设置一致） |

> 注：现网 0.2.1 引擎的 `pnpm-workspace.yaml` 里这六个键写的是 `set this to true or false`，即当时**没跑**这些构建脚本。新装的 staging 反而更完整（终端、FFI、打包器都是真构建）。这是升级后值得观察的行为差异，不算缺陷。

### 10.2 三层架构

```
界面层   外壳/renderer/topbar-status.js  「⋯ 更多 → 引擎更新」折叠项（进度条 + 三个按钮 + 备份列表）
   ↑ IPC
控制层   外壳/main.js  topbar:update-*     6 个 handler；长任务走异步 + webContents 推进度
   ↑ spawn（用机器配置里的 nodeExe）
数据层   工具/引擎更新.mjs                 status / prepare / apply / rollback / clean
         工具/引擎更新检查.mjs（已有）       check（版本比较、engines 校验、端口探测）
```

落盘位置：`12-源码照搬/引擎更新/`（与 `引擎/` 同级，**不入库**，需加 `.gitignore`）
- `staging-<version>/` 装好待应用的完整引擎（约 526 MB/份）
- `backup-<旧版本>-<yyyymmddHHMM>/` 替换前的整目录备份（约 508 MB/份）
- `state.json` 上次结果、当前通道、待应用版本

### 10.3 状态机与按钮

| 状态 | 界面表现 | 可点的按钮 |
| --- | --- | --- |
| `idle`（本地 = 最新） | 「已是最新 0.2.1-rc.3」灰字 | 检查更新 |
| `has-update` | 琥珀提示「有新版本 0.2.2-rc.1」 | 检查更新 / 下载并准备 |
| `preparing` | 进度条 + 「下载依赖 320/620」 | —（可取消） |
| `ready`（staging 已自证） | 「0.2.2-rc.1 已准备好，重启后生效」 | 立即更新 / 丢弃 |
| `applying` | 进度条 + 「备份中 / 替换中 / 验收中」 | —（不可中断） |
| `done` | 「已升到 0.2.2-rc.1，验收全过」 | 检查更新 / 回到 0.2.1-rc.3 |
| `failed` | 红字 + 具体卡在哪一环 | 回到 0.2.1-rc.3 |

后台动作（`prepare`）分四步，每步都写 `state.json`，断电/关窗后可从这四步续上：
1. 下 tarball（`https://registry.npmmirror.com/@deepseek-ai/dsh/-/dsh-<v>.tgz`）并校验 sha
2. 解包到 `staging-<v>/`，写 `pnpm-workspace.yaml`（`allowBuilds` 六项 true）
3. `pnpm install`（用机器配置里的 node + 全局 pnpm；`--registry` 镜像）
4. 自证：`node lib\bin.js -V` 必须等于目标版本；`web --dump-config` 必须 exit 0

### 10.4 「立即更新」为什么要重启

引擎整目录被运行中的 node 进程占着（Windows 文件锁），**不能热换**。所以「立即更新」的真实动作序列是：

1. 主进程写 `引擎更新/pending.json`（目标版本）
2. 主进程用 `nodeExe` **detach** 拉起 `引擎更新.mjs apply`（脱离 Electron 生命周期）
3. 主进程 `app.quit()`
4. 子进程等端口 3083 关闭（最多 90 秒）→ 备份 → 换入 → `环境适配.mjs --apply` → `自检.mjs`
5. 验收全过 → `start "" 启动.vbs` 自动起回来；任一环失败 → 自动把备份 rename 回来 → 写 `state.json: failed` + 原因，**不再自动启动**（交给用户看提示）

### 10.6 与现有「回退（界面 / 引擎）」区块的关系

现有区块管的是**配置级**回退（`profiles/web` 的 cordis 系配置），新区块管**版本级**回退（整目录）。两者不能混：

| | 现有「回退（界面/引擎）」 | 新增「引擎更新」 |
| --- | --- | --- |
| 救什么 | 配置改坏了、插件接错了 → 引擎起不来 | 升了版本发现不对 → 退回旧版本 |
| 粒度 | 几个 KB 的 yml/json | 整目录 508 MB |
| 工具 | `工具\引擎快照.mjs`（**当前不存在，五个 IPC 全报"找不到"**） | `工具\引擎更新.mjs`（新增） |

> 副作用要一起修：现有那 5 个 IPC（`engine-snapshot` / `-restore` / `-gens` / `-restore-gen` / `engine-status`）因为工具缺失，界面上「标为正常」「回到正常」「回到这一代」三个按钮点了必然弹"找不到 工具\引擎快照.mjs"。做更新功能时**同批补齐这个工具**，否则新界面旁边挂着一块点不动的旧界面。

### 10.7 风险与边界（写进代码的硬约束）

1. **只动两处**：`12-源码照搬/引擎/` 与 `12-源码照搬/引擎更新/`。⛔ 不碰 `引擎数据/.dsh` 下会话/日志/凭证（`.credentials.yaml` 不进任何备份/快照）。
2. **替换前必须确认端口空闲**：3083 被占（工作台开着）→ 直接拒绝并提示"先退出工作台"，不做"冒险试试"。
3. **空间闸门**：磁盘余量 < 1.2 GB 时不允许 prepare；备份数超上限时先由用户点「清理旧备份」，不自动删（删的是唯一退路）。
4. **自证不过不替换**：`-V` 不匹配或 `dump-config` 非 0 → 直接判 prepare 失败，旧引擎原封不动。
5. **验收不过自动回滚**：apply 的五关（端口空闲 → 备份成功 → 换入成功 → `环境适配 --apply` exit 0 → `自检` exit 0）任一失败，立即 rename 回退，并保留 `backup-failed-*` 供排查。
6. **断网不假报**：`prepare` 失败一律落在 `failed`，绝不把"没下完"写成"已就绪"。
7. **回退也要验收**：把旧引擎换回来之后同样跑 `自检.mjs`，不通过就说明连备份都不可信，直接报出来让人介入。

### 10.8 已拍板（2026-11-13 用户确认）

| 项 | 结论 | 落地表现 |
| --- | --- | --- |
| 更新通道 | **不指定版本，永远跟 registry 当下的 `latest`** | 工具每次现取 dist-tags，代码里没有任何版本字面量；`next` 只在悬停提示里展示，不自动跨通道 |
| 点「立即更新」的体验 | **两种都做，默认一键** | 主按钮「立即更新（会重启）」走 停机→备份→换入→探活→自动重开；旁边留「下载并准备」给不想被打断的时候 |
| 本次是否真升 | **先不升，只交付功能** | 交付时引擎仍是 0.2.1-rc.3；升不升由用户点按钮决定 |
| 备份保留 | 2 份（约 1 GB），由用户点「清理旧备份」触发 | 不自动删；删的是唯一退路 |

> 「长期功能」的含义写清：**以后官方怎么发版都走同一套 prepare/apply/rollback**。新增依赖由 `pnpm install` 自然带上；`cordis` 次版本升级由 staging 的整棵依赖树自然对齐；`web-app` 自带的新 `cordis.patch.yml` 随包替换。唯一需要人工复验的是**私有插件**（`dsh-token-guard`）与面板契约，见 §三 与 §四 的验收四关。

### 10.9 「检查」这件事归壳，不归外部定时任务（2026-11-13 修正）

第一版把检查做成了「AI 每天跑一次、再在聊天里播报」。那是**外部调度**，不是工作台的功能：关掉那个任务，工作台就瞎了。已撤销（该定时任务已删除），改由外壳自己按点跑：

| 环节 | 落点 | 节奏 / 行为 |
| --- | --- | --- |
| 自动查 | `main.js` ⑥d 段 `updateAutoCheck()` | 壳启动后 40 秒跑一次；之后每 6 小时看一次；**24 小时内查过的不重复联网** |
| 结果落盘 | `12-源码照搬/引擎更新/check.json`（`.gitignore:33` 挡住） | `{ at, check }`，`check` 就是 `引擎更新检查.mjs --json` 的原样输出 |
| 界面读 | `preload` 的 `updateLast` / `updateAuto` | 展开「⋯ 更多」时读 `check.json` 铺一屏，**不点按钮也知道有没有新版**；点「检查更新」走 `updateAuto(true)` 强制刷新并回写 |
| 不涉及 | ⛔ 自动检查只读 | 不下载、不装配、不替换；装与换仍然只有用户点按钮才发生 |

界面上体现为折叠项标题直接带结论：`⇪ 引擎更新 · 有新版本 0.2.2-rc.1（本地 0.2.1-rc.3）· 点开看`，已是最新时显示 `已是最新 0.2.1-rc.3`。

> 端口占用、Node 版本、私有插件、`latest` 三个渠道这些都照旧在展开后显示，数据源是同一个只读检查脚本 —— 只有「什么时候查」从"我这边定时"改成了"壳自己按节奏"。
