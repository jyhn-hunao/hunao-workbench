# 项目记忆与场景记忆 · 自动维护规则（2026-11-11 定稿）

> 目标：**用户不手动触发维护**。每小时自动跑一次；项目记忆与场景记忆都由同一条规则维护。
> 本规则是 `doc\记忆能力改造设计.md` 的补充；两者冲突时以本规则为准。

---

## 0. 七项拍板（用户逐条确认）

| # | 问题 | 结论 |
|---|---|---|
| 1 | 触发事件 | **每小时一次**（不是"完成/决策/坑"事件驱动） |
| 2 | 每小时做什么 | **脚本机械维护 + 只有候选才叫 AI**（无候选零 token 空跑） |
| 3 | 候选信号 | **项目中新提交** + **记忆索引不一致**；未提交改动、会话活动不算 |
| 4 | 执行者 | **复用「命令」场景的 AI 会话**（不新建会话、不占开发会话） |
| 5 | 写回范围 | 项目记忆 + 场景记忆**都写**；**只追加、不压缩、不归档** |
| 6 | 运行窗口 | **工作台开着才跑**；启动时距上次 >1 小时则**补跑一次** |
| 7 | 与即时写回的关系 | **决策/坑即时写；完成类（功能流转）留给整点维护** |

## 1. 一次维护做什么

### 1.1 机械维护（每小时，无论有无候选）

对每个登记项目（`_共享记忆\项目.json`，且存在 `<根>\memory\`）：

1. `node 工具\记忆.mjs index --project <根>`：重建 `_索引.json`、刷新类 README 自动区。
2. `node 工具\记忆.mjs card --project <根>`：刷新薄卡自动区（保留手写区）。
3. `node 工具\记忆.mjs check --project <根>`：记录失败项（供候选判定）。
4. 以上失败只记日志，不中断其它项目。

> 机械维护**不改正文**；只修可再生的索引/薄卡。

### 1.2 候选判定（决定是否叫 AI）

| 候选 | 判据 |
|---|---|
| 新提交 | `git -C <根> log <lastHead>..HEAD --oneline` 非空；无 `lastHead` 时用 `--since=<lastRun>` |
| 索引不一致 | `check` 返回非 0，且失败项含「索引过期 / README 自动区过期 / 薄卡缺失或超限 / 重复标题」 |
| 明确不算 | 未提交改动、会话消息、时间到点、纯 HTML/图片变化 |

有任一候选 → 进入 1.3；否则本次结束（只写日志）。

### 1.3 叫醒「命令」会话

- 主进程 spawn `node 工具\提示会话.mjs --session <命令会话id> --text-file <临时prompt.md>`。
- 命令会话 id 从 `外壳\scenarios\command.json` 的 `panels[cmd-chat].sessionId` **运行时读取**，不写死。
- prompt 上限 2 KB，格式固定：

```
【记忆维护·自动】
候选：
- 项目 mlw：3 个新提交（<hash> <标题> / …）
- 项目 X：索引不一致（<失败项>）
要求：
1) 先读 doc\记忆维护规则.md、项目薄卡、memory\MEMORY_INDEX.md；
2) 只补「完成类」缺的条目与漏写的决策/坑；场景 §〇/§五 只追加，不压缩；
3) 写项目 memory 正文 + 薄卡 + index，跑 check；
4) 无论写没写，都在 <根>\memory\_维护回执.json 记 {"at":"<ISO>","project":"<名>","wrote":N,"note":"…"}；
5) 不自动 git commit，不碰代码。
```

### 1.4 回执与水位（防重复叫醒）

- `_共享记忆\_维护状态.json`：

```json
{
  "version": 1,
  "lastRun": "ISO",
  "lastSuccess": "ISO",
  "projects": { "mlw": { "head": "<sha>", "indexOk": true } },
  "pending": { "project": "mlw", "at": "ISO", "tries": 1 }
}
```

- 发出 prompt 后写 `pending`，**不前移** `projects.head`。
- 下次运行：该项目 `memory\_维护回执.json` 的 `at` 晚于 `pending.at` ⇒ 回执已到，前移 head、清 pending。
- 回执未到且 `pending.tries < 2` ⇒ 重发一次；`tries = 2` 仍无回执 ⇒ 写 `_共享记忆\_待办.md` 一行、前移 head、清 pending（不再每小时纠缠）。
- 单实例锁 `_维护状态.lock`（存在且未过期则本次直接退出）。

## 2. 写回分工（与技能的关系）

| 内容 | 什么时候写 | 谁写 |
|---|---|---|
| 关键决策 | **当场** | 开发会话（`code-dev` 技能） |
| 踩坑修复 | **当场** | 开发会话 |
| 功能流转 / 完成类 | **整点维护** | 命令会话（本规则） |
| 索引 / README 自动区 / 薄卡 | 整点 + 当场写后 | 脚本 |
| 场景 §〇 进度、§五 规矩 | 整点追加；当场的决策/坑也顺带记一行 | 命令会话 / 开发会话 |

- 同一条事实只写一处；整点维护先读已有条目，**不重复写**。
- 完成类若在整点前被用户追问，开发会话可立即补写，不必等整点。

## 3. 失败、日志、例外

- 日志 `_共享记忆\_维护日志.jsonl`：`{at, phase(scan|mechanical|prompt|done), project, ok, detail}`；保留最近 200 条（超过轮转）。
- 机械维护失败：记日志，继续下个项目；下一小时重试。
- 提示会话失败（token/引擎/会话忙）：10 秒后重试 1 次；仍失败按 §1.4 的 tries 规则处理。
- 工作台停机：不跑；下次启动若距 `lastRun` >60 分钟，启动 15 秒后补跑一次（只补一次，不逐小时回放）。
- 用户当轮说「这次别记」：跳过本次并记日志。
- 敏感信息（密钥/账号/token）不写；靠执行者守则，脚本不做内容审查。
- 某项目暂停维护：`项目.json` 该项加 `"maintenance": false`。

---

## 4. 不做什么

- 不压缩 §〇/§五、不自动归档（用户明确选了「都写但不压缩」）。
- 不自动 `git commit` / `git push`。
- 不把未提交改动当候选，不读会话内容做判断。
- 不在每小时无条件叫 AI；无候选时零 token。
- 不改代码、不碰项目仓库里 memory/ 以外的文件。
