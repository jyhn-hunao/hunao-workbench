# 回信路由（dsh-reply-router）

「消息从哪来，就回哪去」的硬闸。解决 2026-11-24 实测问题：在场景「胡闹的大肥鱼」的对话框里发「早上好，饭团」，人格主会话的助手正文是空的，实际调了两次 `qq_send` 把「早。刚扒了口饭，还热着。」发到 QQ。

## 问题怎么来的

1. `dsh-onebot-channel` 把 `qq_send` 注册成**全局工具**，所有 DSH 会话都能看到；
2. 它的工具描述写着「正文永远停在会话里，**只有调了这个工具消息才会出去**」；
3. 人格主会话的历史里留有以前共用一个会话时的 QQ 消息（`（QQ 私聊·用户本人 QQ …）`），模型据此把面板对话当成 QQ 聊天；
4. 结果：面板里说的话，模型用 `qq_send` 往 QQ 回；面板这一轮没有正文，用户看到「对话框去找社交通道回复」。

## 它做什么

1. `agent/pre-step` 每轮判断**真实来源**（优先级从高到低）：
   - 正文带通道前缀：`（QQ 私聊…）/（QQ 群…）/（微信私聊…）/（微信群聊…）/（飞书…）` → `channel`；
   - 已登记在 `社交会话.json` / `微信会话.json` / `qq-bridge.config.json routes` 的会话 → `channel`（QQ 会话额外允许「带 rpcId、无前缀」判成面板里手打的消息）；
   - 带 `rpcId` 且不在登记表 → `panel`（工作台面板 / DSH 网页输入框）；
   - 其余 → `local`。
   为什么不能「有 rpcId 就判面板」：微信通道 `_callSession` 走引擎 RPC，投进会话的用户消息也带 `rpcId`（2026-11-24 实测 `session-8d0cf133…` 的 3 条微信消息都有），只看 rpcId 会把微信正常回信误拦。QQ 入站不带 rpcId，所以 QQ 会话可以安全地区分「面板手打」。`clientTimeZone` 不作为判据。
2. 面板 / local 来源追加一条【回信路由】规则：正文就是回复，不要调 `qq_send / qq_pass / qq_close / qq_wait / qq_qzone_post / qq_group_notice / qq_group_sign / dsh_im_group_file`；历史通道消息不代表本轮来源。
3. 注册 `tools.guard` 硬闸：面板来源的回合里，通道发送类工具一律拒绝执行；通道来源的回合照常放行（不影响 QQ / 微信 / 飞书正常回信）。
4. 例外：用户本轮明确写「发到 QQ / 发到微信 / 发到飞书 / 在微信里说一句」才放行外发。
5. 每次判断 / 注入 / 拦截写 `DSH_HOME\logs\reply-router.jsonl`（只记 sessionId、来源、工具名，不记正文）。

## 不做什么

- 不改 `dsh-onebot-channel` / 微信通道 / 飞书通道源码；只挂引擎公开扩展点 `agent/pre-step` + `tools.guard`。
- 不替代通道自己的发送、@ 触发、群窗口、防刷屏。
- 不拦查询类工具（`qq_msg_history`、`qq_emoji_search`、`qq_face_preview`、`dsh_im_group_history` 等）。
- 不把面板回合的回复「代发」到面板：面板的回复就是模型正文，不需要工具。

## 安装

```powershell
node 12-源码照搬\工具\回信路由.mjs --check
node 12-源码照搬\工具\回信路由.mjs --apply
node 12-源码照搬\工具\回信路由.mjs --mode shadow   # 只记日志、不注入不拦截
node 12-源码照搬\工具\回信路由.mjs --off           # 从 patch 摘掉
```

装完/改完必须**重启整壳**（`启动.vbs`），引擎启动时才会加载插件；不要只重启引擎。

## 验证

- 单测：`node 12-源码照搬\插件\回信路由\自检.mjs`（本机 39 项，含 pre-step 注入模拟与 `ctx.inject` 挂闸；登记表为空时跳过 2 项）。
- 挂闸方式：Cordis 真库 A/B 两种加载顺序（`tools` 服务先到 / 插件先装）都能在服务就绪后挂上 `guard`；不依赖插件加载先后。
- 2026-11-24 10:30 实测（旧加载方式）：在「胡闹的大肥鱼」面板发「重新回，刚才你弄错了」，日志出现 `kind=route origin=panel` + `kind=inject`；助手正文回到面板（「弄错了，那是面板说的话，我不该往 QQ 送。早上好。」），该轮 0 次 `qq_send`。
- 注意：10:29 启动的引擎加载时 `tools` 服务还没就绪，日志是 `guard registered:false`；新版改用 `ctx.inject` 等 `tools` 就绪后再挂硬闸，**需再重启一次整壳**，重启后日志应为 `guard registered:true`。
- 重启后：在「胡闹的大肥鱼」对话框发一句与 QQ 无关的话，`logs\reply-router.jsonl` 应出现 `kind=route origin=panel` + `kind=inject`；若模型仍试图 `qq_send`，应出现 `kind=deny tool=qq_send`，且面板有正文回复。
- 正常 QQ 私聊：应出现 `origin=channel allow=true`，`qq_send` 不被拦。

## 已知边界

- 微信投递的用户消息也带 `rpcId`，所以判定顺序是「前缀 > 登记表 > rpcId」，不是「rpcId 优先」。
- 在**已登记的微信 / 飞书会话**里从面板手打的消息无法和通道入站区分（两者都带 rpcId、都有前缀/登记），会按通道处理；QQ 会话能区分（QQ 入站不带 rpcId）。
- 若某个通道的投递正文既没有前缀、会话也没登记，会按 `local` 处理（不放行通道工具）——这是有意的 fail-closed。
- 插件只拦**工具调用**；QQ 插件的 `autoForwardReply` 自动转发仍由通道自己按投递队列执行，面板会话没有投递队列，不会被误转发。
- 安装版：本次只装进源码 `profiles\web`；下次打包前要把 `插件\回信路由` 加进 `外壳\package.json` 的 `extraResources`，并在 `种子数据\profile-web-cordis.patch.yml` 加一条 `reply-router`，否则新装包没有这道闸。
