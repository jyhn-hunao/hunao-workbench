## 1. 先分清两个同名的 dsh-im（装错会白折腾）

社区里有两个都叫 `dsh-im` 的插件，定位完全不同：

| | A：`@xmanrui/dsh-im` | B：`dsh-im-bridge`（npm `dsh-im` 是它的核心包） |
| --- | --- | --- |
| 规模 | 3118 星 / 12.5 万下载 / MIT / 有官方赞助徽章 | 核心 + 通道分包（`dsh-im-feishu` 等） |
| 定位 | AI 作为 IM 居民（有自己的机器人身份、主动开口） | 人在 IM 里遥控 agent 派活 |
| 渠道 | 单包内置 13 个：飞书、微信(iLink)、钉钉、企微、企微应用、QQ、Slack、Telegram、Discord、WhatsApp、iMessage、Matrix(实验) | 飞书、企微、Telegram、微信 四个分包 |
| 多机器人 | 每个渠道可接多个机器人，工作区/模型/会话绑定各自独立 | 单机器人 |
| 主动投递 | 支持（`botId + targetId`） | 无 |
| 会话反查 | 宿主只读服务 `dshIm.describeConversation(sessionId)` | 无 |
| 权限模型 | 设置页里按机器人调白名单 | `cordis.patch.yml` 里 `allowlist` / `admins` / `trustOnFirstContact` |

**结论：本项目选 A（`@xmanrui/dsh-im`）。** 原因是第 6 节那两个接口——面板要靠它们出「哪个渠道、哪个群、谁说的」。

## 1.1 身份形态：接进来的是 bot，不是普通社交账号

2026-11-13 用户指出、并经插件文档核实：这些通道给的是**机器人身份**，不是「一个正常的微信号/QQ 号」。

| 通道 | 她实际是什么 | 能不能像人一样被加好友 |
| --- | --- | --- |
| 飞书 | 企业自建应用机器人（扫码创建或 App ID + App Secret） | 可被拉群、被 @；但不是成员账号，不会出现在组织架构里当“人” |
| 企业微信 | 自建应用 / 智能机器人 | 同上，成员看到的是应用 |
| QQ | 官方 QQ Bot（手机 QQ 扫码创建，AppID + AppSecret） | 可被加好友、拉群，但平台标为 Bot |
| 微信 | 扫码用的是你手机上的微信，换回的是绑在你账号下的 iLink 机器人凭据（`ilinkai.weixin.qq.com` 长轮询） | 否 |

结论：官方通道给的是「可被找到的 bot 入口」，不是「一个正常微信号」。要让她“像真人”出现在微信/QQ 里，只有独立小号 + 协议端这一条路，封号风险落在小号上——本仓不搭协议端。

对产品的影响：她的自我认知必须是“助理/机器人”，面板和人格里都不许伪装成真人；`describeConversation` 返回的 `senderIsBot` 也是按这个模型给的。

## 4. 飞书接入（应用已建，走手动绑定）

两条路，A 都支持：

1. **扫码创建**：设置页「飞书」→ 扫码 → 手机飞书确认，自动建应用并写凭据。
2. **手动绑定（已有应用走这条）**：填 App ID + App Secret。凭据只交给本机 Host，写入受保护凭据存储，状态接口不回传。

所需租户权限（扫码新建会默认申请，手动绑定的要自己补）：

- `im:message`、`im:resource`（收发消息与上传/下载图片文件）
- `im:message.group_at_msg.include_bot:readonly`（收「其他机器人 @ 当前机器人」的消息，群聊场景必需）

已有应用可在设置页点「补全权限」，或在私聊里发 `/repair` 增量补全，仍需过飞书侧发布审批。

## 5. 安全：装完第一件事是收白名单（不要跳过）

A 的 README 明确写着：**扫码新建的飞书和 QQ 机器人，默认允许所有用户在私聊和群聊中聊天、执行内置命令。**
所以顺序必须是：绑定机器人 → 立刻进「访问设置」把白名单收到只剩自己（或指定成员）→ 再开始接任务。晚配这一步，等于把一个能读写文件的 agent 挂在公网上。

B 的默认相反（默认拒绝 + 首接触触发「信任确认」，管理员 `/trust` 放行），这点 A 更宽松，需要人工补上。

## 6. 面板要用到的三个接口（这是接工作台的关键）

- **`dshIm.describeConversation(sessionId)`** —— 宿主只读服务。返回 `null`（该会话不属于任何 IM 对话）或
  `{ channel, botId, botName, conversationKey, chatType, chatId, threadId, chatTitle, senderId, senderName, senderUsername, senderIsBot }`。
  `chatType` 为 `group` / `thread` / `dm`。只读、不联网、不建会话、不抛错。
- **`dshImClient`** —— 可选客户端服务，宿主可嵌 IM 管理面板；支持全局面板的 DSH 还会在左侧边栏放「IM机器人」。
- **主动投递** —— `botId + targetId` 发文字，设置页能从已聊会话选目标并测试路由；私聊还可开「会话双向同步」（Web/CLI 里该私聊的对话同步回 IM）。

**工作台面板的数据口径**：面板不直读各家私有格式，改为「DSH 会话转录取消息流 + `describeConversation` 补渠道/群/发言人」。转录解析复用 `工具/派发-公共.mjs` 的 `transcriptOf` + `unzstdAll`（多帧 zstd 已修，不要重写）。

口径三条（别在下一次改动时放松）：

1. **消息只认真人说的**：`user/message` 里混着引擎注入的 `agent-instructions` / `runtime-context` / `skill-catalog` / `time-context`，

2. **通道不许画绿**：`ok` 只在 OneBot 端口真在听时给；装了插件没起协议端是 `warn`（琥珀）、没装是 `off`。
3. **换会话不失效**：`so-msg` 的 `sessionId` 过期时按 `sessionTitle`（「社交」）从投影缓存里重新认近日那条，面板不会因为换过会话就永远空着。

界面要生效必须**重启整壳**（主进程与 preload 改了，见 AGENTS.md §8，不要在壳外重启引擎）。

群聊记录另有一条独立存储：A 默认采集实际收到的群消息与附件，滚动保留 **14 天**，在「IM机器人 → 齿轮 → 通用」里改。它只存「实际收到的」，不回填历史。

## 7. 数据落在哪、换机器会丢什么

- 机器人默认工作区：`$DSH_HOME/im`（未设置时为 `~/.dsh/im`），实际选用时才创建。本仓 `DSH_HOME` 指向 `12-源码照搬/引擎数据/.dsh`。
- 凭据：写入 Host 受保护存储，不进状态接口、不进 git。
- 会话映射与群记录：插件自己的状态文件（A）；B 落在 `$DSH_HOME/dsh-im/mappings.json`、`approvals.log`、`im-inbox/<chatId>/`。
- **换机器**：凭据要重配、机器人要重连；`sessionId` 是本机数据，搬过去必然失效（同 AGENTS.md §8）。群记录是否随迁，取决于状态文件在不在 `$DSH_HOME` 里。

## 10. SnowLuma：源码自建跑通（2026-11-13，本轮唯一活路）

发行包断供之后，用户拿到 `D:\MyApp\SnowLuma-main.zip`（12.1 MB / 1268 条目 / sha256 `42c6a74e…d1d0ce`），

三条口径：

1. **生命周期归壳**，和引擎同一条规矩（AGENTS.md §8）：壳起它就起、壳关它就关。
   `autoStart()` 先用 pid 文件收掉"上次壳崩了遗留的那只"，**绝不**见 5099 有在听就杀（可能是别人的服务）。
2. **不常驻面板**：控制台不进顶栏图标（`hidden`），入口只有 `so-msg` 标题右边那颗 `⚙ 桥接`；
   点一下 = 先 `snowlumaStart()`（没起就拉起）→ 再 `__kunWebAiOpen('snowluma', true)` 开浮动窗口。
   登录态走 `persist:webai-snowluma` 分区，登一次之后点开就是登好的。
3. **不许拿 `process.execPath` 拉它**：壳里那是 `electron.exe`，拉起来等于再开一个 Electron（现象是"点了没反应"）。
   所以 `桥接.js` 用 `cfg.nodeExe` → `SNOWLUMA_NODE` → PATH 里的 `node`，本机配的是 `C:\Program Files\nodejs\node.exe`。
