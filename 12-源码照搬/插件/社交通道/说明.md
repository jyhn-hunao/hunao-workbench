## 1. 先分清两个同名的 dsh-im（装错会白折腾）

社区里有两个都叫 `dsh-im` 的插件，定位完全不同：

| | A：`@xmanrui/dsh-im` | B：`dsh-im-bridge`（npm `dsh-im` 是它的核心包） |
| --- | --- | --- |
| 规模 | 3118 星 / 12.5 万下载 / MIT / 有官方赞助徽章 | 核心 + 通道分包（`dsh-im-feishu` 等） |
| 定位 | AI 作为 IM 居民（有自己的机器人身份、主动开口） | 人在 IM 里遥控 agent 派活 |
| 渠道 | 单包内置 13 个：飞书、微信(iLink)、钉钉、企微、企微应用、QQ、Slack、Telegram、Discord、WhatsApp、iMessage、Matrix(实验) | 飞书、企微、Telegram、微信 四个分包 |
| 多机器人 | 每个渠道可接多个机器人，工作区/模型/会话绑定各自独立 | 单机器人 |
| 主动投递 | 支持（`botId + targetId`） | 无 |
| 会话反查 | 宿主只读服务 `dshIm.describeConversation(sessionId)` | 无 |
| 权限模型 | 设置页里按机器人调白名单 | `cordis.patch.yml` 里 `allowlist` / `admins` / `trustOnFirstContact` |

**结论：本项目选 A（`@xmanrui/dsh-im`）。** 原因是第 6 节那两个接口——面板要靠它们出「哪个渠道、哪个群、谁说的」。

## 1.1 身份形态：接进来的是 bot，不是普通社交账号

2026-11-13 用户指出、并经插件文档核实：这些通道给的是**机器人身份**，不是「一个正常的微信号/QQ 号」。

| 通道 | 她实际是什么 | 能不能像人一样被加好友 |
| --- | --- | --- |
| 飞书 | 企业自建应用机器人（扫码创建或 App ID + App Secret） | 可被拉群、被 @；但不是成员账号，不会出现在组织架构里当“人” |
| 企业微信 | 自建应用 / 智能机器人 | 同上，成员看到的是应用 |
| QQ | 官方 QQ Bot（手机 QQ 扫码创建，AppID + AppSecret） | 可被加好友、拉群，但平台标为 Bot |
| 微信 | 扫码用的是你手机上的微信，换回的是绑在你账号下的 iLink 机器人凭据（`ilinkai.weixin.qq.com` 长轮询） | 否 |

结论：官方通道给的是「可被找到的 bot 入口」，不是「一个正常微信号」。要让她“像真人”出现在微信/QQ 里，只有独立小号 + 协议端这一条路，封号风险落在小号上——本仓不搭协议端。

对产品的影响：她的自我认知必须是“助理/机器人”，面板和人格里都不许伪装成真人；`describeConversation` 返回的 `senderIsBot` 也是按这个模型给的。

## 4. 飞书接入（应用已建，走手动绑定）

两条路，A 都支持：

1. **扫码创建**：设置页「飞书」→ 扫码 → 手机飞书确认，自动建应用并写凭据。
2. **手动绑定（已有应用走这条）**：填 App ID + App Secret。凭据只交给本机 Host，写入受保护凭据存储，状态接口不回传。

- `im:message`、`im:resource`（收发消息与上传/下载图片文件）

已有应用可在设置页点「补全权限」，或在私聊里发 `/repair` 增量补全，仍需过飞书侧发布审批。

## 5. 安全：装完第一件事是收白名单（不要跳过）

A 的 README 明确写着：**扫码新建的飞书和 QQ 机器人，默认允许所有用户在私聊和群聊中聊天、执行内置命令。**
所以顺序必须是：绑定机器人 → 立刻进「访问设置」把白名单收到只剩自己（或指定成员）→ 再开始接任务。晚配这一步，等于把一个能读写文件的 agent 挂在公网上。

B 的默认相反（默认拒绝 + 首接触触发「信任确认」，管理员 `/trust` 放行），这点 A 更宽松，需要人工补上。

## 6. 面板要用到的三个接口（这是接工作台的关键）

- **`dshIm.describeConversation(sessionId)`** —— 宿主只读服务。返回 `null`（该会话不属于任何 IM 对话）或
  `{ channel, botId, botName, conversationKey, chatType, chatId, threadId, chatTitle, senderId, senderName, senderUsername, senderIsBot }`。
  `chatType` 为 `group` / `thread` / `dm`。只读、不联网、不建会话、不抛错。
- **`dshImClient`** —— 可选客户端服务，宿主可嵌 IM 管理面板；支持全局面板的 DSH 还会在左侧边栏放「IM机器人」。
- **主动投递** —— `botId + targetId` 发文字，设置页能从已聊会话选目标并测试路由；私聊还可开「会话双向同步」（Web/CLI 里该私聊的对话同步回 IM）。

**工作台面板的数据口径**：面板不直读各家私有格式，改为「DSH 会话转录取消息流 + `describeConversation` 补渠道/群/发言人」。转录解析复用 `工具/派发-公共.mjs` 的 `transcriptOf` + `unzstdAll`（多帧 zstd 已修，不要重写）。

1. **消息只认真人说的**：`user/message` 里混着引擎注入的 `agent-instructions` / `runtime-context` / `skill-catalog` / `time-context`，

2. **通道不许画绿**：`ok` 只在 OneBot 端口真在听时给；装了插件没起协议端是 `warn`（琥珀）、没装是 `off`。
3. **换会话不失效**：`so-msg` 的 `sessionId` 过期时按 `sessionTitle`（「社交」）从投影缓存里重新认近日那条，面板不会因为换过会话就永远空着。

界面要生效必须**重启整壳**（主进程与 preload 改了，见 AGENTS.md §8，不要在壳外重启引擎）。

群聊记录另有一条独立存储：A 默认采集实际收到的群消息与附件，滚动保留 **14 天**，在「IM机器人 → 齿轮 → 通用」里改。它只存「实际收到的」，不回填历史。

## 7. 数据落在哪、换机器会丢什么

- 机器人默认工作区：`$DSH_HOME/im`（未设置时为 `~/.dsh/im`），实际选用时才创建。本仓 `DSH_HOME` 指向 `12-源码照搬/引擎数据/.dsh`。
- 凭据：写入 Host 受保护存储，不进状态接口、不进 git。
- 会话映射与群记录：插件自己的状态文件（A）；B 落在 `$DSH_HOME/dsh-im/mappings.json`、`approvals.log`、`im-inbox/<chatId>/`。
- **换机器**：凭据要重配、机器人要重连；`sessionId` 是本机数据，搬过去必然失效（同 AGENTS.md §8）。群记录是否随迁，取决于状态文件在不在 `$DSH_HOME` 里。

## 10. SnowLuma：源码自建跑通（2026-11-13，本轮唯一活路）

发行包断供之后，用户拿到 `D:\MyApp\SnowLuma-main.zip`（12.1 MB / 1268 条目 / sha256 `42c6a74e…d1d0ce`），

### 12.1 选型：不接 webhook，走「插件换脑」

鲸鲸官方定位是「用你的微信账号陪聊」，不是通用 IM SDK。两条路比过：

| 路 | 做法 | 结论 |
| --- | --- | --- |
| 纯桥接 | `WHALE_BOT_URL` 指向工作台，自己实现 `/healthz`、`/api/bridge/heartbeat`、`/api/wechat/send-permission`、`/api/vision`、联系人同步、care/reminders | 否决：协议面太大，维护量高 |
| **插件换脑（采用）** | 鲸鲸 4.1.2+ 的 JavaScript 插件 Api 4；只挂 `chat.generate`，把「已判定要回」的消息转到 31241 适配器，回复写回 `{text}` | 保留鲸鲸自己的私聊接、群聊 @/名字、冷却/防刷屏；工作台只负责人格与记忆 |

关键执行链（`src/pipeline/chat.js`）：`decide()` 先判定是否接话；只有 `decision.action === 'reply'` 时才跑
`chat.prompt` → `chat.generate`。`chat.generate` 返回 `{text}` 会替换本轮模型调用；返回空串 =
`decision.action='ignore'`（`reason='plugin_empty'`），即「这一条不回」——**不会回落到鲸鲸自己的模型**。

### 12.7 边界与坑（已遇到/已修）

- **官方 Python 是 embeddable 版**：`python312._pth` 里的 `.` 相对 `runtime\python`，不是 cwd；
  `python -m bridge` 报 `No module named bridge`。改为直接跑 `bridge\__main__.py`（它自己把
  `bridge/`、`examples/` 塞进 `sys.path`），并保留 `PYTHONPATH=home` 兜底。
- **sitecustomize 不能只靠 PYTHONPATH**：embeddable Python 实测不读 `PYTHONPATH` 里的
  `sitecustomize`，补丁看似装了其实没生效。`_installSitecustomize` 现在复制到
  `runtime\python\Lib\site-packages\sitecustomize.py`，解释器启动即加载；换鲸鲸版本后
  要确认这个文件还在（`_startBridge` 每次启动会重新复制）。
- **微信数据目录是 Junction 时账号比对会误判**：`D:\MyApp\...` 是别名，psutil 打开文件拿
  到的是 `D:\电脑管家迁移文件\...`；占位文件曾多拼一层 `db_storage`，导致鲸鲸把当前账号
  读成 `db_storage`。现在 `DSH_WX_ACCOUNT_DIR` 用 `fs.realpathSync` 的真实路径，占位文件
  直接放在 `db_storage` 下；账号匹配再用 `windowHwnd` 做兜底。
- **DSH `user/message` 不带 `turn`，marker 不能只查带 turn 的事件**：DSH 的
  `user/message` 事件只有 `content`/`source`，marker 在这条事件上；紧跟的
  `step/start`、`assistant/message`、`turn/end` 才带 `turn`。旧代码只找「带 turn 且
  JSON 含 marker」的事件，永远 `markerTurn=0`，等满 110 秒超时 → 插件 `plugin_empty`
  → 工作台明明有回复，微信却不发。`findMarkerTurn` 现在先定位 marker 事件，再向后取
  第一个带数字 turn 的事件；实测同一轮 `turn=4`，`finalTextOf` 能取到
  「饭团。一条住在工作台里的胖鱼，专管杂事。」。
- **钉账号必须同时钉窗口**：只写 `wechat.account`、不写 `wechat.windowHwnd`，鲸鲸在
  Junction 目录上会报「没扫到微信主窗」。工作台每次启动只按**唯一可见主窗**重新写
  `windowHwnd`；看到多个主窗就不猜，先把另一个微信窗口关掉。主窗缩到托盘/最小化也仍然
  算「唯一主窗」——补丁按 `GetWindowPlacement` 的还原矩形识别，不会因为最小化就判 0。
- **桥接的模块名是顶层名，不是 `bridge.*`**：`bridge/app.py` 用 `import engine as G`、
  `from account_mixin import AccountMixin`，所以 `sys.modules` 里是 `engine`/`account_mixin`。
  兼容补丁的账号放行线程必须两种名字都认，只找 `bridge.account_mixin` 会永远等不到、
  `_window_account_matches` 不会被替换（症状：桥接一直「没扫到微信主窗」）。
- **CLI 自检看不到壳里的 31241**：`selfCheck` 现在会探测
  `http://127.0.0.1:31241/healthz`，不再只看当前 Node 对象的 `serverListening`；
  从壳面板跑和从命令行跑都应显示「适配器在听」。
- **`whale.delivery` 长期 pending**：桥接日志已经 `发送成功（后台通道）`，SDK 仍可能停在 pending。
  `sendTest` 现在同时看 `delivery` 和桥接日志增量（发送前记 offset，只留本次新增行，最多等 16 秒），
  避免把成功误报成未确认。
- **UIA 没就绪就发 = 排队不动**：桥接刚起时日志会写 `微信窗口未唤醒`，此时把消息塞进队列可能一直 pending。
  `sendTest` 现在先等 UIA（最多 60 秒），超时直接报“发送通道 UIA 还没就绪”，不乱发。
- **文件传输助手不能当入站测试**：鲸鲸 `_decide` 把「文件传输助手」硬编码进系统号名单，入站消息会被
  `system_notice` 忽略。它只用于**出站**自检；要测入站，用另一个微信好友/小号发。
- **`sendText` 的 `chatId`**：私聊用桥接上报的 `chatId`（通常 sender wxid），群聊用群 id；`filehelper` 只用于自检。
- **4.2.0.13 的 gate**：本机 UIA 物化成功（`Weixin.dll+0xb50abc8`，gate 0→1）；微信小版本升级后要重跑自检，
  失败时先看 `whale-bridge.log` 有没有 `物化成功`，不要直接改代码。

## 13. QQ 通道：重启后自动注入，且双开只接指定号（2026-11-19）

**现象**：电脑重启后再开工作台，SnowLuma 的 5099 控制台在、QQ 也在，但 3000 / 3001 不监听；
「社交 → 通道」QQ 卡片显示「协议端未起」，必须进控制台点一次「加载」才恢复。
双开时更糟：如果自动注入不挑号，会把主号和小号一起挂上。

**根因（已核实到源码）**：SnowLuma 的 `config/runtime.json` 里 `hookAutoLoad` 默认 `false`
（`packages/common/src/runtime.ts:48`，`packages/core/src/index.ts:63` 读它；
上游只在 Docker 部署的 supervisord 里打开）。它不会在发现 QQ 进程时自动注入 Hook，
所以重启后 QQ 是全新进程、没人注入 ⇒ OneBot 会话不启动 ⇒ 3000 / 3001 不监听。
而它的 `hookAutoLoad` 是「发现即全注入」，不按 QQ 号过滤 —— 不能直接拿来双开。
**OneBot 网络配置本身是持久化的**：`dist/config/onebot_<uin>.json`（`mode:"snapshot"`），
账号一登录就 `network startup applied`，不需要每次重建；缺的只有「按号注入」这一步。

**修法（2026-11-19 第二版：按号挑）**：
1. `外壳\桥接.js` 拉起 SnowLuma 时固定 `SNOWLUMA_HOOK_AUTOLOAD=0`，关掉它自带的全量注入。
2. 新模块 `外壳\QQ自动注入.js` 接管：登录 5099（`POST /api/login`）→ 拉 `/api/processes` →
   只注入 `autoLoadUin` 指定的号：
   - 进程命令行带 `--from-multiple-login <uin>` 的，直接认号，直接注入；
   - 认不出的，按「最早启动优先」逐个试注入（`POST /api/processes/<pid>/load`），
     等登录；登录出来的号不是目标就 `POST /api/processes/<pid>/unload`，试下一个；
   - 目标已在线上 → 卸掉其它已注入的号（含手动注入的），只留目标；
   - `autoLoadProbe:false` 时只认命令行提示的号，不盲试。
3. 配置在 `外壳\data\桥接.json`（本机文件，已 gitignore）：
   `autoLoadMode`（`uin` / `all` / `off`）、`autoLoadUin`、`autoLoadProbe`、
   `webuiPassword`（控制台改过密码才需要填；缺省用 `bootstrapPassword`）。
4. 面板入口常驻：社交 → 通道 → QQ 卡片「默认接入 QQ 号」块 ——
   下拉选「只接指定号 / 本机全部 / 不自动」，填号点「保存号」；写配置并立即重新识别。
   本机当前值：`autoLoadMode=uin`、`autoLoadUin=2531357970`、`autoLoadProbe=true`。

**边界（必须知道）**：
- 「试注入」会短暂把非目标号挂上 Hook（通常 2–15 秒），确认不是目标后立即卸载。
  这是 QQ 9.9 不回答 `pt_login`、进程列表也不带号时唯一可靠的识别办法；不想盲试就把
  `autoLoadProbe` 设为 `false`（代价：只能接命令行带号的实例，否则要进控制台手动加载）。
- 已知不是目标的号（命令行带号 / 已登录）不会被注入；目标在线上时，其它已注入的号会被强制卸载。
  所以双开时请确保 `autoLoadUin` 填的是小号，**不要填主号**。
- 自动注入要登录 5099：控制台密码改过之后，把新密码写进 `webuiPassword`；否则状态显示
  「控制台登录失败」，不会乱注入（宁可不接，也不接错号）。
- 3000/3001 的网络配置仍归 SnowLuma 的 `onebot_<uin>.json`，本模块不碰。

**验证（2026-11-19 10:11 / 10:29）**：
- 真实 5099：对运行中的 SnowLuma 调 `POST /api/processes/25436/load` 后，
  `snowluma.log` 出现 `[Hook] login detected: PID=25436 UIN=2531357970` →
  `[OneBot.HTTP] listening 127.0.0.1:3000/`、`[OneBot.WS-Server] listening 127.0.0.1:3001/`；
  插件日志 `~/.dsh/qq-bridge-load.log` 在 `02:11:04Z` 出现 `[ws] 已连接 ws://127.0.0.1:3001/`，
  之前的 `OneBot HTTP 502` 轮询错误停止 ⇒ 面板数据面恢复。
- 假 SnowLuma 模拟（127.0.0.1:5098，两进程：pid 100 登录目标号、pid 200 登录别的号）：
  目标 `2531357970` → `load:100` 一次，pid 200 完全不动，状态 `connected`；
  目标 `7777777777` → `load:100 → unload:100 → load:200 → unload:200`，最终 `waiting`，
  两个进程都回到未注入 ⇒ 双开「只留指定号」的状态机跑通。
- **未验证**：新面板（保存号/输入框）和整壳重启后的真实链路要等下一次重启工作台才跑到；
  判据：`snowluma.log` 有 `[QQ注入]` 行（「已接 2531357970（只接这个号）」等），随后
  `[Hook] login detected`，3000/3001 在听，`qq-bridge-load.log` 有 `[ws] 已连接`。

**排障顺序**：① 看 `snowluma.log` 有没有 `QQ 自动注入：由壳按 QQ 号挑`（没有 = 壳还是旧进程，重启整壳）；
② 有没有 `[QQ注入]` 行；③ 有「控制台登录失败」→ 改 `webuiPassword`；
④ 有「没找到 QQ X」→ 确认 QQ 已登录、进程在跑，或看面板「本机 QQ」那一行的 pid 与状态；
⑤ 3000/3001 在听但面板仍红 → 看 `qq-bridge-load.log` 的 `[ws]` 与 `[poll]`，再看闸门 3100。
