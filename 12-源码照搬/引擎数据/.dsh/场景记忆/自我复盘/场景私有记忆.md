## 五、坑与决策

- 2026-11-11（现象先行）：用户说"卡住"时，**先拿到那一屏**（截图 / `boot:state` 快照 / DOM 探针），再回日志找判据。上轮我扎进 2.1MB 日志，90% 是 `[wv:inject]` 噪声，绕了端口、进程、注入循环三圈，最后是 `.tmp-diag\shell-window.png` 一张截图把"92% + 引擎已就绪，正在加载界面…"定死的。改法：第一动作固定为「拍屏 + 拿状态」，日志只用来对判据。
- 2026-11-11（现场残留）：开工先扫上一轮的残留物。`.tmp-diag\` 是 18:20 另一轮诊断留下的（`server.log.before`、`shell-window.png`、`shot.ps1`、2 字节的 `run.log`）——说明**上轮排障没写结论就断了**，现场白留一夜。改法：见到 `.tmp-*` / `captures` / `*.before` 先读，能接上就接，接不上就先补一条结论，别让它烂在那。
- 2026-11-11（调用点）：改共享入口函数前先 `grep` 出**全部调用点**再改。`renderer.js` 的 `loadHarness()` 有 3 处调用（`init()` 末尾 / `harness:ready` 事件 / 点标签），我第一版加了"最多等 10s"，会让 `init()` 在冷启动早期干等 10s 后误报"取不到 token"，把进度条盖掉。虽然提交前自查拦下了，但这是本来一条 grep 就能避免的返工。
- 2026-11-11（提交与推送分步）：**先 commit，看 `git show --stat` 与 `git diff --numstat`，确认干净再 push**。我把 `commit && push` 写成一条命令跑完，推完才看到 `renderers.js` 484 行行尾噪声；因为"已推送不改写历史"，只能追加 `9fb6db5` 去还原——历史里永久多了一条噪声提交。代价小，但规则上完全可避免。
- 2026-11-11（行尾）：改混合行尾的大文件，编辑工具会按主导行尾重写，CRLF 段被统一成 LF ⇒ 1 行改动变 242/242。改前先记 `git diff --numstat` 基线（应为空），改完立刻复核；噪声已产生就 `git checkout <rev> -- <file>` 还原，再用 .NET `ReadAllText/Replace/WriteAllText(UTF8Encoding($false))` 只替换目标行。
- 2026-11-11（改记忆）：记忆里的「当前状态区」（§〇 的待办 / 表格）要**逐行替换**，别整段重写。我整段替换 §〇「下一步」时，把别人留下的"第二个项目进来走 `project-onboarding`"删掉了，第二轮对比才发现补回。
- 2026-11-11（证据与推断分开写）：本次"现在这一轮也命中竞态"是**推断**（依据日志顺序 + 上一轮的截图），不是直接观测（我看不到那屏）。结论里要把"日志能证明的"和"推断的"分开，并写清缺哪条证据——否则用户没法判断可信度。
- 2026-11-11（先破错误前提）：讲机制先破用户最可能的错误前提。第一轮我只说"token 晚到"，用户下一句就是"我不是配置了吗"——因为没点破"它不是配置项、没有任何文件能配它"。以后遇到"某凭据/开关拿不到"，先一句"这东西是不是配置项"再讲时序。
