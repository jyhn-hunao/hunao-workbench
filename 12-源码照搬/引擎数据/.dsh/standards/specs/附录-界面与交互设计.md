# 附录：界面与交互设计（反黑盒 / 反人类）

> 解决的问题：AI 写界面时很容易把「功能能跑」当成「界面可用」——核心入口藏在图标、右键或长弹层里，默认值替用户做了危险决定，单击和双击互相打架，刷新一次把用户输入清空，出错只在角落闪一行小字。
> 用户看到的就是一个黑盒：不知道能做什么、现在在哪、点下去会发生什么、做错了怎么退。
> 本附录只规定「可发现、可理解、可恢复」的通用判据，不规定具体配色和像素；颜色、尺寸、组件类写进项目规则。

---

## 0. 一句话原则

> **先让用户看得见入口、看得懂状态、退得出流程，再谈好看；任何核心能力都不能只活在图标、右键菜单或长弹层里。**

### 0.1 两个定义

| 词 | 在本规范里的含义 | 典型表现 |
| --- | --- | --- |
| **黑盒设计** | 用户无法从界面本身发现能力、状态和后果 | 入口只有图标；点开是长弹层；没有空态 / 失败态；操作后无反馈；不知道数据从哪来 |
| **反人类设计** | 界面让用户多做、容易错、错了难恢复 | 默认全选 / 默认提交；单击直接执行危险动作；双击和单击冲突；刷新清空输入；删除无确认；关键按钮被卷出屏幕 |

---

## 1. 六条硬底线（不可豁免）

项目可以规定更细的值，但不得放宽这六条：

1. **入口可见**：核心操作必须有常驻可见入口；不能只藏在图标、右键菜单、「更多」或长弹层里。图标按钮必须有文字标签或 tooltip，关键操作优先「图标 + 文字」。
2. **默认安全**：默认值不能替用户做提交、删除、覆盖、发送等不可逆决定；批量列表默认不选中；默认视图优先给源内容，派生视图（diff / 汇总 / 预览）作为显式选项。
3. **一次一件事**：一个入口只做一类任务；复杂任务拆成步骤或独立卡片；禁止用一个长弹层同时塞分组、排除、提交等多个任务。
4. **状态可见**：空、加载、成功、失败、禁用、无权限、部分成功都要有明确文案和下一步；不能只靠颜色、动画或图标表达状态。
5. **可退出、可恢复**：弹层能关闭、流程能取消、错误能返回；破坏性操作必须两步确认或可撤销，并写清影响范围。
6. **反馈明确**：操作成功 / 失败必须有用户能看见的反馈；错误要说明「哪一环失败、现在怎样、下一步怎么做」；关键结果不能只放在会消失的小字里。

> 视觉一致性、主题、对比度属于第 7 条底线，见 §7；它是「看得清」的底线，不是锦上添花。

## 2. 动手前必须写清的九件事

界面 / 交互改动进入实现前，先在方案里写清下面九项。缺任何一项，不得直接写代码；M / L 级仍按主规范 §2 先给方案等确认。

| # | 必须写清 | 要回答的问题 | 反例 |
| --- | --- | --- | --- |
| 1 | 用户与主任务 | 谁用、在什么场景用、这次只帮他完成哪一件事 | 「优化一下 UI」 |
| 2 | 入口与位置 | 核心入口在哪个常驻区域；次要入口在哪；为什么不能只放右键 / 图标 / 弹层 | 只留一个 `⋯` 或 `◧` |
| 3 | 默认值与持久化 | 第一次打开是什么状态；默认为什么不危险；用户改过的选择是否记住、怎么重置 | 打开就全选、默认直接提交 |
| 4 | 状态矩阵 | 空、加载、成功、失败、禁用、无权限、部分成功分别显示什么 | 只画成功态 |
| 5 | 单击 / 双击 / 右键 / 键盘 | 各自负责什么；单击是否只选中；双击功能有没有单次替代入口 | 单击直接弹 diff，双击先触发两次 click |
| 6 | 危险操作 | 哪些动作不可逆；如何确认；能否撤销；确认文案是否写清对象和范围 | 「确认删除？」不写删什么 |
| 7 | 跨面板联动 | 谁触发、通知谁、目标怎么定位、目标不存在时怎么提示 | 点了没反应，也不报错 |
| 8 | 数据来源与权限 | 界面上的值从哪来；没有权限 / 数据缺失时显示什么 | 凭空造字段、空占位 |
| 9 | 验收用例 | 正常、边界、异常各一条；哪条只能静态推断、哪条未实跑 | 只写「已优化」 |

> 这九项和主规范 §4「数据来源 / 输出契约 / 边界状态 / 停止条件」是同一套思路在界面层的展开，不是另一套流程。

## 3. 入口与信息层级

### 3.1 核心入口

- 主任务入口必须**常驻可见**，不能依赖用户先发现一个图标、右键或「更多」。
- 图标按钮只用于全站已经形成共识的动作（关闭、搜索、刷新等），并且必须有 tooltip；提交、删除、排除、切换查看模式这类关键动作必须带文字。
- 「更多」菜单只能放次要动作，**不能成为核心能力的唯一入口**。
- 同一能力不要同时存在多个互相竞争的入口；必须有主入口，其他入口是快捷方式。

### 3.2 分组与层级

- 全局操作放顶部，组级操作放组头，行级操作放行尾或右键；不要让用户猜「这个按钮作用在哪一层」。
- 长弹层只做一件事。超过两类任务、超过一屏、需要用户来回滚动对照的，拆成独立卡片 / 弹窗 / 分区。
- 空组、空列表也要画出来，作为拖拽落点或下一步入口；不能因为「没数据」就整块消失。

### 3.3 当前模式必须可见

- 有模式切换（内容 / 改动、列表 / 卡片、编辑 / 预览）时，必须显示**当前模式**，不能只显示一个图标。
- 模式选择要能持久化，并在下次打开时恢复；同时提供恢复默认的路径。

## 4. 默认值、模式与持久化

### 4.1 默认值

- 批量列表默认**不选中任何项**；提交、删除、发送只作用于用户显式选中的对象。
- 默认动作必须是可逆或只读的；默认不能替用户提交、删除、覆盖、发送。
- 查看类功能默认优先给**源内容**；diff、汇总、预览是派生视图，应作为显式选项。业务上必须默认派生视图时，要在方案里说明理由。
- 默认值是产品决策，不是实现细节；不能因为「代码里正好是这个值」就当成默认。

### 4.2 持久化

- 用户显式改过的模式、排序、筛选、折叠状态，能持久化就持久化；存储位置服从项目规则。
- 持久化值损坏或不存在时，回退到安全默认，并让用户能看出来当前模式。
- 不把「上次会话的临时选择」当成永久偏好；临时状态和长期偏好分开存。

### 4.3 自动刷新与用户状态

- 自动刷新不能清空用户已经输入的草稿、勾选、选中项、滚动位置。
- 刷新前后内容没变，不要重画 DOM；内容变了，也要尽量保留用户状态。
- 用户正在操作（打开弹窗、拖拽、输入）时，暂停自动刷新或延后到操作结束。
- 后台更新成功但用户没看见时，用轻量提示告诉用户「已更新」，不要静默替换。

---

## 5. 一次一件事与危险操作

### 5.1 复杂任务拆分

- 一个弹层只完成一个任务；变更单管理、排除规则、提交信息、移动分组应各自独立。
- 复杂流程必须有「上一步 / 取消 / 关闭」；不能一路走到黑。
- 弹层内容超高时，底部操作区必须 sticky，不能让主按钮被卷出可视区。
- 弹层要有遮罩、背景、边框 / 阴影、圆角；点遮罩或 Esc 能关闭（危险确认除外），关闭后焦点回到触发按钮。

### 5.2 危险与不可逆操作

- 删除、覆盖、提交、发送、批量移出等动作，必须两步确认或提供撤销。
- 确认文案必须写清**对象、数量、范围、后果**，不能只写「确认删除？」。
- 优先软删除 / 移出 / 可撤销；例如「从分组移出」只改归属，不碰磁盘文件。
- 危险按钮不能是默认焦点；默认焦点放在取消或安全动作上。
- 不允许「一键删组顺带删文件」「默认全选后提交」这类把风险藏在默认值里的设计。

## 6. 单击、双击、右键与键盘

| 输入 | 负责什么 | 硬规则 |
| --- | --- | --- |
| 单击 | 选中 / 聚焦 / 展开 | 有双击动作时，单击**只能**做选中或聚焦，不能执行危险或弹窗动作 |
| 双击 | 打开 / 执行主查看动作 | 必须另有右键菜单或按钮提供**单次替代入口**，不能只靠双击 |
| 右键 | 快捷动作集合 | 只能作为快捷方式，不能是核心能力的唯一入口 |
| 键盘 | 可达性 | 主要动作有 Enter / Space / Esc；弹层有焦点陷阱，关闭后焦点回到触发点 |

补充：

- 双击功能必须有可见提示（如「双击看 内容 / 改动」），不能让用户猜。
- 单击和双击不能竞争：如果单击会打开弹窗，双击时第一次 click 已经触发，用户会看到两个结果。正确做法是单击只选中，双击再执行。
- 悬停才出现的按钮，必须在键盘聚焦时也出现；不能只服务鼠标用户。
- 行内按钮、组头按钮、右键菜单的文案要写清作用对象，不能只写「编辑」「删除」。

## 7. 状态、反馈与视觉可读

### 7.1 状态矩阵

每个界面至少检查：

- **初始态**：第一次打开看到什么，主任务入口在哪。
- **加载态**：加载什么、加载多久、能否取消；不能用一个假进度条假装。
- **空态**：没有数据时显示什么、下一步能做什么；不能只显示「暂无数据」。
- **失败态**：哪一环失败、影响范围、能否重试；不能只写「操作失败」。
- **禁用态**：为什么禁用、满足什么条件才能用；不能只把按钮变灰。
- **无权限 / 只读**：能看什么、不能做什么、如何申请权限。
- **部分成功**：哪些成功、哪些失败、失败项怎么处理。

### 7.2 反馈

- 操作结果用项目统一的通知 / toast / 状态条；错误信息停留时间要够读，项目没有规定时错误至少 8 秒或需要手动关闭。
- 关键结果不能只放在面板标题行、会消失的小字或 console 里。
- 失败提示必须包含：哪一环、当前状态、下一步动作；不能把异常吞掉只留一行空日志。
- 批量操作完成后要告诉用户成功多少、失败多少、失败项在哪。

### 7.3 视觉可读

- 颜色、字号、间距、圆角一律服从项目设计令牌和组件类；禁止内联写死颜色、禁止裸原生控件。
- 正文不小于项目规定的最小字号（没有规定时不低于 12px）；次要文字对比度不低于 4.5:1。
- 浅色和深色两套主题都要检查；「深色下看着没问题」不等于浅色下没问题。
- 状态不能只靠颜色表达：红 / 绿之外要有文字或图标；涨跌、成功 / 失败、选中 / 禁用都要有非颜色线索。
- 焦点态、悬停态、禁用态、选中态必须可区分；不能只靠鼠标悬停才看得见。

## 8. 跨面板 / 跨视图联动

- 任何会改变另一个面板的界面动作，必须写清：谁触发、传什么、目标怎么定位、失败怎么提示。
- 目标面板不存在、目标文件已删除、目标行找不到时，必须有可见的兜底提示；不能静默失败。
- 跨面板定位要尽量做到「翻到父级 → 选中目标 → 滚到可见」，并在完成后把焦点留在目标上。
- 一个动作如果需要用户同时看两个面板，必须在界面上说明另一个面板会怎么变；不能靠用户自己发现。
- 从历史 / 快照打开内容时，要区分「当前工作区内容」和「该历史版本内容」；两者对不上时不能假装是同一份。

## 9. 交付与验收（界面改动必附）

界面 / 交互改动交付时，除主规范 §6 的八项外，必须额外附：

| # | 内容 | 判据 |
| --- | --- | --- |
| 1 | 设计说明 | §2 九项逐条有答案，不写「按常规」 |
| 2 | 三个交互用例 | 正常、边界（空 / 长文本 / 窄宽 / 多条）、异常（失败 / 无权限 / 重复点击 / 取消） |
| 3 | 黑盒测试 | 不看代码、不看说明，新用户能否在界面上找到入口、看懂状态、退出流程 |
| 4 | 默认值测试 | 第一次打开是否安全；不勾选 / 不提交 / 不删除是否成立 |
| 5 | 输入冲突测试 | 单击、双击、右键、键盘是否各司其职，是否有重复触发 |
| 6 | 状态保持测试 | 刷新、切面板、重开弹层后，草稿 / 勾选 / 滚动是否还在 |
| 7 | 视觉检查 | 浅色 / 深色、窄宽、长文本、空数据、禁用态、焦点态 |
| 8 | 验证标注 | 已实跑 / 仅静态检查 / 未验证，分开写；不能把静态检查说成 UI 验收 |

> 只写「UI 优化」「已改好」或只贴一张截图，不算界面交付。

## 10. 反模式清单

| 反模式 | 为什么是黑盒 / 反人类 | 正确做法 |
| --- | --- | --- |
| 核心功能只放一个图标 | 用户不知道图标含义，也不知道里面有多个能力 | 图标 + 文字，或常驻文字入口 |
| 一个长弹层塞多类任务 | 用户找不到、要滚动对照、关掉就丢失 | 拆成独立卡片 / 弹窗，一次一件事 |
| 默认全选 / 默认提交 | 用户没做决定，系统替他做了不可逆动作 | 默认不选，只提交显式勾选 |
| 单击直接执行，双击另有动作 | 双击时第一次 click 已经触发，结果不可控 | 单击只选中，双击再执行 |
| 刷新清空输入 / 勾选 / 滚动 | 用户的工作被系统扔掉 | 刷新保留状态，变了再重画 |
| 删除无确认 / 确认不写对象 | 用户不知道删了什么、能不能恢复 | 写清对象与范围，两步确认或撤销 |
| 禁用按钮无原因 | 用户不知道为什么不能点 | 禁用态写原因和开启条件 |
| 错误只在角落闪一下 | 用户错过就不知道发生了什么 | 统一 toast / 状态条，错误够久、可关闭 |
| 只靠颜色表达状态 | 色弱 / 浅色主题下不可读 | 文字 + 图标 + 颜色三重表达 |
| 写死深色常量 | 默认浅色主题下白字白底 | 全走设计令牌，浅 / 深都验 |
| 跨面板操作静默失败 | 用户以为成功了，实际没发生 | 目标不存在时明确提示 |
| 用「UI 优化」代替行为说明 | 审查者不知道改了什么、怎么验 | 写入口、默认、状态、退出和 3 个用例 |

## 11. 自检清单（提交前逐条过）

- [ ] 核心入口常驻可见，关键动作有文字或 tooltip。
- [ ] 默认值安全，没有默认提交 / 删除 / 覆盖；批量列表默认不选中。
- [ ] 一个入口只做一件事，复杂任务已拆成卡片或步骤。
- [ ] 空、加载、成功、失败、禁用、无权限、部分成功都有文案和下一步。
- [ ] 弹层能关闭 / 取消，Esc 和遮罩可用，焦点能回到触发点。
- [ ] 危险操作有两步确认或撤销，确认文案写清对象和范围。
- [ ] 单击只选中；双击有单次替代入口；右键不是唯一入口。
- [ ] 自动刷新不会清空草稿、勾选、选中项和滚动位置。
- [ ] 跨面板联动有目标定位和失败提示，不静默失败。
- [ ] 颜色 / 字号 / 组件走项目令牌，没有内联写死颜色和裸原生控件。
- [ ] 浅色 / 深色、窄宽、长文本、空数据都检查过。
- [ ] 交付附正常 / 边界 / 异常三个交互用例，并标明未验证项。

## 12. 与主规范、项目规则的关系

- 主规范 §14 是本节的总入口；本附录是展开判据。项目规则可以规定更严的视觉值和组件规范，但不能放宽 §1 六条硬底线。
- 冲突裁决仍按主规范 §0.2：**用户当轮指令 > 铁律层 > 项目层 > 个人偏好层 > 技术栈 / 附录默认值**。
- 规则类改动要说明同步了哪些文件：主规范、本附录、项目规则入口、常驻记忆（如有）。
- 视觉令牌、组件类、具体字号属于项目值，必须能从目标仓库文件找到证据；找不到就列入待确认，不能拿本附录当项目事实。
